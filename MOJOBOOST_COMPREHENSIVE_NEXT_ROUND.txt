MOJOBOOST COMPREHENSIVE PARALLEL NEXT ROUND

HOW TO USE THIS FILE

Each TASK below is a complete standalone prompt for one Claude Code session. Copy and paste one entire TASK section into one session. Start every desired session at the same time. These tasks are designed for parallel execution in the same shared mojoboost repository. Do not combine two tasks in one session. Do not create branches, worktrees, clones, or alternate checkouts.

This round is for implementation and integration, not machine validation. Every session must obey all of these rules:

- Inspect git status and the relevant files before editing.
- Stay strictly inside the task's owned files and directories.
- Preserve all unrelated and concurrent changes. Never revert, overwrite, reformat, stage, commit, or clean another session's work.
- If a required change belongs to another lane, write the exact requested change in the task handoff. Do not edit the other lane's files.
- Do not run tests, test suites, Mojo programs, Python programs, Pixi commands, pip, builds, wheel builds, examples, benchmarks, profilers, formatters, linters, CI jobs, Docker, network services, polling loops, retry loops, watchers, or background processes.
- Do not run broad validation under any name. Do not attempt to prove performance or correctness during this round.
- Lightweight static inspection is allowed: rg, sed, git status, git diff, git diff --check, wc, and reading files.
- Tests may be designed in the handoff, but do not write or execute test code in this round unless the task explicitly owns a named new test-plan document. The objective is useful implementation work without consuming local CPU.
- Do not commit, push, publish, upload, tag, release, dispatch workflows, change repository settings, or contact external services.
- Keep Mojo authoritative for training, prediction, data representation, objectives, metrics, tree logic, serialization, and accelerator policy. Python is a thin ergonomic and ecosystem layer.
- Match current LightGBM names and semantics where users rely on them. Preserve documented MojoBoost improvements. Reject conflicting aliases. Do not reproduce deprecated or file-config-only behavior merely to inflate parity.
- Never claim a feature is complete merely because code exists. Distinguish implemented, integrated, publicly reachable, focused-tested, differential-tested, hardware-validated, and release-packaged.
- End by writing the task's owned handoff file. Report files changed, behavior implemented, behavior intentionally deferred, cross-lane requests, risks, and the smallest focused commands a later validation coordinator should run. Clearly label every command UNRUN.

All tasks are parallel. Task numbers indicate organization, not execution order. No task should wait for another task. Where another lane's future output is needed, code against the smallest documented interface or produce a handoff request and continue with all independent work.
