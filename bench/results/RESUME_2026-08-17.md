## The MVS lane's four-cell design, which is step 2

Both exits work TODAY with no code change. `bootstrap_type` is exposed, so this
is a legitimate default question under rule 9.

- **D control** MVS 0.8, `random_strength=1.0`. Host arm, 2 hessian planes.
- **A** MVS 0.8, `random_strength=0.0`. Host arm, 2 planes.
- **B** Bayesian, `random_strength=0.0`, `subsample` DELETED. Device arm, 2
  planes. **B minus A is the clean price of the host round.**
- **C ship candidate** `bootstrap_type='No'`, `subsample` DELETED,
  `random_strength=1.0`. Device arm, 1 plane.

Two traps the lane found. **`subsample` must be DELETED, not set to 1.0**, or a
fixup turns it into row bagging every tree and lands back on the host arm. And
**Bayesian forces `random_strength` off** (`ROUND_BAYESIAN_NOISE_SCALE`), so
switching MVS to Bayesian and changing nothing else leaves the round on the host
arm. Set `MOJOTREES_GPU_OBJECTIVE=device` so a mis-specified cell RAISES instead
of silently downgrading, and `MOJOTREES_GPU_SPLIT_TRACE=1` now prints a line on
every arm.

Arm dicts live in `bench/real_data/scenarios.py`, the run-shape lane's file, so
these cells need adding after it lands.

**New from the histogram lane, four switches, all default OFF:**
`MOJOTREES_GPU_HIST_LEAN`, `_PRIVATE`, `_ROW_SPLIT`, `_GROUP`. Its two findings
worth more than the ideas themselves:
- **9.3 no-op threadgroups per working one** on the oblivious level build, each
  writing about 3 KB of threadgroup memory read by nothing. About 32 GB of dead
  threadgroup stores per 360-tree fit. `HIST_LEAN=1` measures the removal alone,
  and it is category 1 (strictly less work, same result).
- The oblivious level build runs a **primitive** kernel while the leaf-wise path
  runs a 40-instantiation specialized family with feature grouping (measured
  1.17x at G=2), quantized gradients and const-hessian elision. None of it
  reaches the batched kernels. That is the ranked follow-on.
- Zero atomics is **not reachable** in Mojo 1.0 (no warp primitives, so the
  smallest unit is the threadgroup and 256 threads x 3.1 KB busts a 32 KB
  budget). The knob reduces contention by a replication factor instead, free at
  low bin counts because the planes are already allocated at full width.
- Idea 2's premise was **partly false**: `plan_slots` is the feature count, 100,
  constant across depth, so there is no shallow-depth starvation on the headline
  shape. Built anyway, priced as a likely null at 100 features and a win where
  `n_slots < 80`.
