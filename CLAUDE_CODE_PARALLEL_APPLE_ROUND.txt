MOJOBOOST IMMEDIATE PARALLEL DEVELOPMENT ROUND
==============================================

Purpose
-------

This file defines an IMMEDIATE parallel development round. Start every task
at the same time, including while current sessions are wrapping up. Task 11
(objective, metric, and weighting coverage) is already in progress and is
therefore not duplicated here.

Every lane owns distinct primary implementation and test files. Each lane
implements working code now, runs only its own smallest focused test, and
writes an integration handoff. Broad suites, unrelated tests, benchmarks,
wheel builds, and release validation wait; coding and focused validation do
not wait.


GLOBAL PARALLELISM CONTRACT
===========================

Every task repeats this contract so it can be copied independently.

- Start immediately. Do not wait for other sessions, stabilization, a commit,
  or another task.
- Inspect current code and `git status` read-only before editing.
- Preserve all concurrent work.
- Edit ONLY the paths explicitly assigned to your task.
- New parent directories assigned to you may be created.
- Do not edit shared hotspots: `README.md`, `pixi.toml`, `pixi.lock`,
  `.github/workflows/*`, `bindings/_mojoboost.mojo`,
  `python/mojoboost/__init__.py`, `src/mojoboost/__init__.mojo`,
  `src/mojoboost/boosting.mojo`, `src/mojoboost/tree.mojo`,
  `src/mojoboost/model.mojo`, `src/mojoboost/serialize.mojo`,
  `src/mojoboost/train_gpu.mojo`, `src/mojoboost/histogram_gpu.mojo`,
  `docs/LIGHTGBM_PARITY.md`, or existing tests.
- If central wiring is required, describe the exact imports, calls, fields,
  ABI changes, serialization changes, and documentation changes in your
  assigned `handoffs/*.md` file. Do not make those edits yourself.
- Do not commit, stage, stash, switch branches, create worktrees, rebase,
  revert, or clean files.
- Run exactly ONE smallest focused test covering your assigned work. A Mojo
  lane may run its one assigned new Mojo test file. A Python lane may run its
  one assigned new pytest file. A documentation/design-only lane runs no test.
- If the focused test cannot run until central integration, run no substitute
  suite; explain the blocker in the handoff.
- Do not run broad suites, existing unrelated tests, `pixi run test`,
  `pixi run test-gpu`, the whole Python test directory, wheels, all
  benchmarks, profilers, parity scripts, or CI.
- Do not run retry loops, polling loops, watch commands, sleeps, background
  commands, or multiple commands in parallel.
- `git diff --check -- <your assigned paths>` is also required.
- Write narrow tests in the assigned new test file and run only that file
  when it can execute independently.
- Never claim that unrun code compiles, passes, is faster, or reaches parity.
- Stop after implementation plus handoff. Report assigned files changed,
  central integration required, focused test command and result, and risks.

POST-PARALLEL INTEGRATION — DO NOT ASSIGN DURING THIS ROUND
==========================================================

After every parallel session has stopped:

1. Create a preservation commit containing all isolated outputs.
2. Review every `handoffs/*.md` file and reject duplicated or incompatible
   designs before touching central files.
3. Assign ONE integration owner for shared Mojo training/model/serialization
   files and ONE integration owner for Python/bindings/docs; do not let them
   edit the same paths simultaneously.
4. Wire one subsystem at a time in dependency order:
   active rows -> split search -> GPU objectives/runtime -> GPU prediction ->
   Apple policy/device UX; independently EFB/tree parameters/inspection;
   then CV/distributed/Dask; finally packaging/docs.
5. During integration, run one focused test at a time. Never run multiple
   Mojo compilers concurrently.
6. Run the full suite only once, on explicit user request, after focused
   integration is green and no other Claude or Mojo process is active.
